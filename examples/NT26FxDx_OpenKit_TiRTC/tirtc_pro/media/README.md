# 共用音频硬件与 Opus / G.711 适配

AI、微信电话、设备电话、LIVE 和 Room 共用同一 ES8311 录放硬件。派生自 [小钛利尔达参考](https://github.com/tangeai/xiaotai-lierda/tree/f159bfd3e82cc514dfe6b5b2269b2c96fa8e8f93/examples/L_CT4IT00_YP00W_01_V04/tirtc) 的 `audio_device/g711_codec`，保留探鸽版权归属；2026-09-28 按维护者要求将探鸽自有源码统一为 [MIT](LICENSE)，所调用的原厂音频 SDK 仍遵循自身授权。当前接口见 [audio_device.h](audio_device.h)。

新增的 `opus_codec.c/.h` 适配器来自本仓库 Lite 的 [Opus 适配源码](../../tirtc_lite/src/media/opus_codec.c)和[头文件](../../tirtc_lite/include/opus_codec.h)，保留 MIT 版权头，并增加包时长检查与独立解码器重置；实际算法使用公共 [Opus 1.4](../../../../components/thirdparty/opus/opus-1.4/COPYING)，遵循其上游许可。

## 硬件和格式

- ES8311：I²C0 / I²S0，PA 为 GPIO11；模块作主时钟，codec 从机，单声道右通道、16-bit word/slot。
- I²S 对应模组 PAD26/30/31/32/33；PA_SD 为 PAD29；I²C0 SCL/SDA 为 PAD39/38。
- 屏幕端口先启用共享 3.3 V 电源。本模块不反复操作 LCD、触摸或 Flash 的公共供电。
- 硬件工作在 **16 kHz 单声道 PCM16**。20 ms 对应 320 样本、640 字节；公共采集接口每次返回这一帧。默认 AEC 从 SDK 流回调收集 PCM，关闭 AEC 时一次 SDK Record 获取这一帧，不再按旧的 40 ms 批次拆分。
- AI 使用与 Lite 相同的 Opus 适配：16 kHz 单声道，上行每 20 ms 编码一包、目标码率 24 kbit/s、复杂度 3；下行保留完整 Opus 包边界，解码后按最多 320 样本送入硬件。
- Room 网络协议仍为 **8 kHz 单声道 G.711 A-law**：上行将相邻两个硬件 PCM 样本平均，每 20 ms 编码为 160 字节；下行每个 A-law 字节解码后复制为两个相同 PCM 样本，再交给 16 kHz 硬件。单次播放最多 320 个 PCM16 样本。硬件采样率变化不代表网络语音变成宽带。

## 生命周期

1. 业务获得带 owner/generation 的音频租约。
2. `prepare_session()` 初始化或复用 codec，并一次提交有效音量/增益。
3. 单一采集者录音；单一播放生产者提交有界 PCM。业务层管理 Opus / A-law 编解码、抖动缓冲和播放节奏。
4. 控制操作与采播在途状态互斥，不能在短临界区内执行阻塞 SDK 操作。
5. 结束时停止新输入，等待正在执行的 SDK 调用，stop，再 release。BUSY 保留租约并等待，不强行 deinit 或释放旧内存。

默认 `TIRTC_AUDIO_AEC_EN=y` 启用 AEC 和 ANS（`bypass=0, mode=1`，与 Lite 一致），AGC 保持旁路；AI、微信、设备互呼、LIVE 和 Room 共用此配置。使用 F6D_D 3A 回调取新鲜的 20 ms PCM，单次采集最多等待 120 ms；有界播放队列整块接受或返回暂满（`-42`），调用方保留队首并继续服务采集。Stop 先静音，由专用线程等待约 200 ms 后先停录音、再停播放，并重建采集；不能逆转 SDK 的停流顺序。关闭 AEC 时保留普通 Record/Play 路径。

普通 SDK Record 可能无超时等待硬件；Play 复制数据后异步输出；Stop 不是同步 DMA 完成屏障。FINISH、队列空或 AEC 的尾部时间估算只能辅助调度，不能单独作为内存释放依据。

## 开关、音量与首字预热

出厂默认扬声器 8/10、麦克风增益 8/10、两开关开启；已保存配置优先。开关关闭将有效级别静音，但保留用户原数值。硬件映射与 G.711 无关，见源码 `set_levels/apply_levels`。

各业务使用同一份保存的用户音量档位。设备电话与 Room 的播放软件音量固定为 10（单位增益），codec 在用户 1～10 档使用 38～72 的映射表，避免先在软件中放大并削顶、再由 codec 衰减。用户 0 档时 codec 为 0，播放接口跳过语音 PCM 输出；软件音量为 10 不表示解除静音。AI、微信和 LIVE 保留原来的软件及 codec 0～60 映射，本次没有改变这些业务的曲线。麦克风使用与 Lite 一致的公共增益和数字音量表，L1 为 7/160，L8 为 9/190，L10 上限为 9/199，并遵循保存的用户档位与开关；设备电话没有强制改成 L7，出厂默认为 L8。设置页的“麦克风音量”下拉选项可选择 L0（静音）～L10。

开启 AEC 时，由连续采播后端维持时钟，公共预热接口返回 0 额外时长，各业务仍保留自身下行预缓冲。以下 1200 + 80 ms 静音预热仅适用于关闭 AEC 的普通录放音分支。

设备电话采用独立的下行预缓冲，跳过连接静音预热和每段附加静音。Room 在连接准备阶段通过 `prewarm_session()` 提交 1200 ms 静音 DAC 时钟，包括扬声器为 0 档或关闭的入房场景；连接准备可并行进行，但要等预计预热尾时结束后才发 `join_room`，避免把首段语音排在长静音后。Room 仅调整音量或开关扬声器不会使已经完成的连接预热失效，后续新段仍保留 80 ms 短预热。AI、微信和 LIVE 保留原来的预热策略：提前提交 1200 ms，首段补 80 ms；未提前预热时，首段承担完整 1280 ms。以上均不构成端到端时延保证。

连接预热按 150 ms / 4800 字节提交，避免单次调用跨越 SDK 的 5120 字节队列项而漏记已接受的静音。若前缀已经入队而后续提交失败，返回 `WARM_PARTIAL`，业务走正常安全清理，不能当作普通 BUSY 重复整段预热。总静音时长仍为 1200 + 80 ms。

改变音量、静音、停止、换租约会丢弃尚未使用的录音缓存，避免旧录音流入新状态；这不等于已经入队的播放 PCM 被同步撤回。AEC 开启时使用 `use3A` 连续采播，AI 回复期间仍可上传麦克风；Room 保留原按住讲话的发送规则。AEC 关闭时仍使用 `use3A=0` 和原业务播放保护。

## 排查时区分三个结果

- 编码/发送接口接受了音频：不证明远端播放完成。
- SDK Play 接受 PCM：不证明 PA/喇叭已经出声。
- FINISH 或估算音频尾部到达：不证明所有 DMA 资源可立即释放。

常态保留启动和必要错误日志；会话、音量及音频状态通过设备界面查看。真实声音、增益、供电噪声和声学回声须实机听测。完整业务音频路径见 [代码篇](../docs/代码与流程详解.md)，主机检查方法见 [测试说明](../tests/README.md)。
