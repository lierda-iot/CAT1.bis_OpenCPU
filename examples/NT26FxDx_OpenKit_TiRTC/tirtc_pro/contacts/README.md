# 通讯录同步

这是应用层新实现，不改利尔达 SDK。使用正式设备身份的 JWT，同步真实服务器通讯录；没有内置联系人，也不把微信授权状态当成设备在线状态。

## 接口与生命周期

- `tirtc_contacts_start()`：幂等创建一个 16 KiB、优先级 8 的后台任务；任务创建失败可重试，不阻塞 UI。
- `tirtc_contacts_publish()`：仅复制缓存到专用 UI 邮箱，无 HTTP/模组操作。
- `tirtc_contacts_action()`：只合并刷新请求；进入通讯录或刷新按钮可触发同步。
- `tirtc_contacts_lookup(id, wechat, out)`：按稳定 ID 和类型查找，复制微信 app/model 字段及身份/路由代次。过期、同步中、网络变化或解绑时拒绝拨号，调用方仍须在实际请求时复核 context。

只调用 `GET /v1/call/device/contacts`，从 `data.contacts[]` 读取 `type=device/voip`。未知类型不会作为设备拨号。正常每 30 秒刷新，失败按 5/10/20/40/60 秒退避，手动/正式 MQTT 更新提示合并且请求至少间隔 1 秒。绑定身份改变立即清空联系人，临时断网保留名称但标记不可用；缓存超过 60 秒不可用于拨号。

完整 JSON、重复 key、嵌入 NUL、字段类型/长度及 UTF-8 均校验。响应最多 8191 字节（另留终止符），超过整次失败并保留不可用旧缓存。UI 最多 12 人；超出数量明确提示部分未显示。微信 `device_id` 是 OpenID；若同时提供 `wx_open_id` 必须相等。联系人昵称仅在完整 UTF-8 校验后按字符边界截断。日志只含数量、状态和错误，不含 OpenID、JWT 或响应内容。

## AI 使用的新查询票据

AI 呼叫不会直接使用一份旧 UI 列表。它向 contacts 申请新刷新票据，等待对应请求完成后按完整名称/ID 和类型精确唯一匹配；列表超限、无效项或失败时不能证明唯一性，返回明确失败。联系人业务仍由同一个后台任务同步。

名称按服务器的 `remark → device_name → name → nickname` 选择第一个非空值，只匹配这个完整名称或 `device_id`，不是同时匹配全部别名。有备注时不再按被覆盖的昵称匹配；UI 长名称的截断显示也不能用作完整目标。

详细容量、超时、AI 结果码见 [AI 呼叫篇](../docs/AI呼叫微信与设备配置详解.md)；手动操作见 [通讯录](../docs/当前设备操作.md#calls)。
